## What the repair did fix

1. **The original OOB is no longer reachable through the exported API.**
   `EVP_MD_meth_set_app_datasize` → `EVP_DigestInit_ex` allocates exactly
   `digest->ctx_size` (`src/evp/digest.rs:2333,2347`) → `EVP_MD_CTX_ctrl` →
   `evp_md_ctx_ctrl_legacy` (`digest.rs:3680`). The guard compares against the same
   field that sized the allocation:
   ```rust
   // src/evp/legacy_sha.rs:156-157
   let ctx_size = unsafe { (*digest).ctx_size };
   if ctx_size >= 0 && ctx_size as usize >= size {
   ```
   `size` is `size_of::<ShaCtx>()` (`legacy_sha.rs:383-388`); `init_keccak` mirrors
   it (`legacy_sha3.rs:155-158`). The setter refuses a second write
   (`ctx_size != 0`, `digest.rs:1386`), so `N < size_of::<T>()` is refused before any
   write. Verified independently; this contradicts the 2026-10-30 rejection's
   decisive claim, which is why a re-review rather than an override was required.
2. **The vacuous-test finding is fixed.** All nine surface tests now invoke a table
   callback (1/3/5 via `assert_callbacks_refuse`, `legacy_digest_callback_surface.rs:153-226`;
   2 init/update/final; 4 update; 6 init; 7 ctrl; 8 `EVP_md_null`'s three; 9 sha1's three).
   Undersized ctrl through the exported path is covered at `legacy_sha.rs:1305` and
   `legacy_sha3.rs:826` (refusal + byte-identical block).
3. Every guarded callback's size matches the context type it casts to; none writes
   beyond its `size_of::<T>()`.

## New finding — a soundness concern the earlier reviews did not raise

`EVP_MD_meth_set_app_datasize` (`src/evp/digest.rs:1386-1389`) performs **no origin
check**. It therefore writes `ctx_size` into `EVP_ORIG_GLOBAL`, the shared static
returned by `EVP_sha1()` (`legacy_sha.rs:993-998`) — directly contradicting the
`unsafe impl Sync` justification that this state is "never written"
(`legacy_sha.rs:169-172`). A public API can mutate a `Sync` static that other
threads may be reading. This is a separate mechanism from the extent guards and is
**not** covered by B48's boundary list; it must be raised as its own boundary.

Second, related observation: `init_md_data`'s owner-identity arm
(`legacy_sha.rs:151-153`) bypasses the extent check. It is sound today only because
every legacy owner table has `ctx_size: 0` (`legacy_sha.rs:215`,
`legacy_sha3.rs:212`), so `evp_md_init_legacy` allocates nothing (`digest.rs:2336`).
**That invariant is nowhere asserted.**

## Required work before re-application (ordered)

1. Add a test in `src/evp/legacy_sha3.rs` + `legacy_digest_callback_surface.rs` that
   builds a method with `app_datasize >= size_of::<KeccakCtx>()` and `result_size`
   of `0` and `-1`, drives `sha3_int_init`/`shake_init`/`sha3_int_final` through the
   exported getters, asserts `0` and an unchanged block, and **fails if
   `legacy_sha3.rs:162` is deleted**.
2. Add the analogous targeted test for the negative-`ctx_size` branch
   (`legacy_sha3.rs:156`, `legacy_sha.rs:157`), noting it is reachable only through a
   hand-built context.
3. Add a `const` assertion that every owner table passed to `init_md_data` /
   `init_keccak` has `ctx_size == 0`, since the owner arm bypasses the extent check.
4. Raise the `EVP_ORIG_GLOBAL` mutation as its own boundary and either add an origin
   check in `EVP_MD_meth_set_app_datasize` or re-justify the `Sync` claim in light of
   a writer existing.
