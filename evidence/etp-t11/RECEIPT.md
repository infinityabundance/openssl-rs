## 3. What the tool decides

`forensics/tools/scheduling.py` implements seven commands: `tier`, `rules`,
`require`, `cache-put`, `cache-get`, `identity` and `report`. It imports the
change classifier and Git reader from `forensics/tools/freshness.py` rather than
reimplementing them, so the tool identity covers both files.

* **Tier.** Twelve rules map a changed path to a minimum tier; the change set's
  tier is the maximum over its paths. The rule table is data and `rules` prints
  it, so the document and the executed policy are the same object. Two rules
  reach `SEAL` (the exported-symbol script, and a `SAFE_COMPATIBLE` line added to
  or removed from the claim document), four reach `BOUNDARY` (shared mechanism,
  instrument register, independence records, venue), four reach `BATCH` (build
  input, tool, source, unclassified path) and two reach `FAST` (evidence-only,
  documentation). Seventeen declared shared-mechanism paths plus the `src/ffi/`
  prefix; a control asserts every declared path exists.
* **Requirements.** Twenty-five named checks; the sets accumulate, so `FAST` is
  4 checks, `BATCH` 10, `BOUNDARY` 16, `SEAL` 22 and `EXTERNAL` 25.
  `EXTERNAL` is printed but never derived from a change set.
* **States.** `SATISFIED`, `NOT_RUN`, `FAILED`, `REFUSED`, `BLOCKED`, aggregated
  worst-of (`BLOCKED > REFUSED > FAILED > NOT_RUN > SATISFIED`) with per-check
  states, all five counts, the blocked rows with their bounds and the
  `not_satisfied` list. Exit codes: `0` satisfied, `1` not satisfied, `2`
  refusal, `3` cache miss, `4` blocked, `5` cached failure.
* **Cache.** An applicability identity is five fields — source commit and tree,
  tool paths with their digest, instrument name and configuration, target
  profile/triple/features, and the exact population with its digest. The store
  key is the digest of the canonical five fields; entries are re-validated on
  read and written sorted, with no timestamp.
* **Exhaustion.** Every recorded result carries memory, time and disk bounds
  with observed values; `PASS` after exceeding a bound is refused, `BLOCKED`
  without a bound is refused, and a blocked row is visible in every aggregate.

## 6. Findings

* **F1 — the queue's BATCH claims are not bindable.** Across six real change
  sets, the number of requirements genuinely satisfied is zero. This is not a
  report defect: no record in the tree carries the five-field identity the
  reuse rule needs. The claims may be true; they are not reusable, and a later
  change cannot tell whether they still apply.
* **F2 — receipts name the base, not the candidate.** `etp-t9` names
  `26c127262`, `etp-t10` names `7e70b667f` and `haz-16` names `5d38094cc` as
  their identity, and each is the commit *before* the change the receipt
  describes. Even the field that is recorded would identify the wrong subject.
* **F3 — two source change sets that touch the shared stack are not `BATCH`
  changes.** The policy schedules both at `BOUNDARY`, and the records themselves
  say which `BOUNDARY` obligations are `NOT_RUN`.
* **F4 — the exported-symbol script makes a change set `SEAL`.** The Phase-2
  shell records six ABI courts against the authority and none of the `SEAL`
  obligations.
* **F5 — the uniform requirement set over-states the requirement.** A
  documentation change is scheduled at `FAST` and lists `FAST_FMT`; a Python
  tool change is scheduled at `BATCH` and lists the Rust suite. The
  over-statement is deliberate: a per-class exemption is a way for a change to
  schedule itself. The consequence is recorded rather than argued away: **this
  batch's own change set, once committed, requires `BATCH`, and the Rust library
  suite, the affected probes and the affected courts were not run in this batch.
  They are `NOT_RUN`** and are for the integration checkpoint to discharge. The
  work touches no `src/` file.

## 8. What this does not establish

* The tool does not run the checks it names, and a `SATISFIED` aggregate would
  not mean a result is correct — only that a `PASS` is bound to the exact
  claimed identity.
* An exact population is a bound population, not a sufficient one.
* Refusing a prose receipt says the record is not admissible, not that the work
  was not performed.
* `EXTERNAL` is never derived and none is claimed.
* A `SATISFIED` aggregate would not be a graduation; `SAFE_COMPATIBLE` still
  needs every mechanism in the dependency closure to be `SAFETY_DISCHARGED`.
* `TIERS.json` describes the six change sets at the commits named in
  `CHANGE-SETS.json`. It says nothing about `HEAD`.
