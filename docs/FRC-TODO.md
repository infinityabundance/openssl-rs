# Formal Refinement and Certification — work queue

Single tracked queue for `docs/FORMAL-REFINEMENT-CERTIFICATION.md`. Status
vocabulary is inherited from `docs/ETP-TODO.md`.

Every item's result is an ETP claim: bound to a candidate identity, an artefact,
a TCB, a scope and an invalidation rule. An FRC item never upgrades an ETP
verdict by itself; it supplies evidence the verdict may then cite.

Rules that bind this queue:

- match the frontier before claiming to exceed it, and name which property is
  matched and which is added;
- a specification is never generated by restating the implementation, and proof
  automation never closes an obligation by weakening the requirement;
- a proof in a model is not a proof about the deployed binary;
- a tool is admitted only with a pinned version, a theorem class, a TCB, a
  positive control, a negative control and a supported-compiler statement;
- the Adversarial Soundness Laboratory runs against this project's own machinery
  before any external target;
- a published gap is not a defect, and a defect claim survives only reproduction
  and independent examination;
- **do not omit, do not stop, push often.**

## Gating

- `FRC-0` gates everything: no prover is used before it is admitted, and no
  specification is written before the hierarchy is established.
- `FRC-1` and `FRC-2` are independent of each other once `FRC-0` exists.
- `FRC-3` and `FRC-4` both depend on an exact artefact; neither may cite the
  other's evidence.
- `FRC-5` depends on `FRC-1` and `FRC-2` for the kernels it composes.
- `FRC-6` depends on `FRC-5` and on the consumer identity evidence already held
  by the interop courts.
- `FRC-8` requires a declared system context; without one the matrix is produced
  and the certification question stays open.
- `FRC-10` is the demonstration that the chain composes; it does not require
  `FRC-8`, and `FRC-8` does not require `FRC-10`.

`PFP` and `FRC` interact in one direction only: an optimisation is admitted under
PFP only when the FRC evidence for the property it could affect remains valid at
the new digest, and an FRC claim is invalidated by any change to the kernel,
specification or toolchain it names.
